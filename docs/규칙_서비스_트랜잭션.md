# 커넥션 폭풍 방지를 위한 서비스 작성 규칙

이 문서는 H2와 PostgreSQL을 함께 사용하는 우리 프로젝트의 멀티-데이터소스 환경에서, `Max client connections reached`와 같은 커넥션 관련 오류를 원천적으로 방지하기 위한 핵심 개발 규칙을 정의합니다.

---

## 1. 핵심 원칙: 모든 트랜잭션은 명시적으로 관리한다

Spring이 트랜잭션 관리자를 스스로 추측하게 두지 않고, 모든 서비스가 사용할 DB를 코드 레벨에서 명확하게 지정하여 트랜잭션 충돌을 방지합니다.

---

## 2. 서비스 계층(@Service) 규칙

### 규칙 1: 트랜잭션 관리자 명시적 지정

- **내용:** DB 작업을 수행하는 모든 서비스(`@Service`) 클래스는, 클래스 레벨에서 사용할 트랜잭션 관리자를 **반드시 명시**해야 합니다.
- **근거:** 이 규칙을 통해 어떤 서비스가 어떤 데이터베이스와 통신하는지 명확히 하고, 의도치 않은 트랜잭션 충돌을 막습니다.

- **H2 사용 서비스:**

  - **대상:** `com.oath.domain` 및 그 하위 패키지에 속한 모든 서비스
  - **코드:**
    ```java
    @Service
    @Transactional("h2TransactionManager")
    public class MyDomainService { ... }
    ```

- **PostgreSQL 사용 서비스:**
  - **대상:** `com.oath.recommend_domain` 및 그 하위 패키지에 속한 모든 서비스
  - **코드:**
    ```java
    @Service
    @Transactional("pgTransactionManager")
    public class MyRecommendService { ... }
    ```

### 규칙 2: 불필요한 `@Transactional` 제거

- **내용:** 클래스 레벨에 `@Transactional`이 선언된 경우, 속성(e.g., `readOnly=true`)이 없는 메서드 레벨의 `@Transactional`은 중복이므로 제거합니다.
- **근거:** 코드를 간결하게 유지하고, 클래스 레벨의 설정을 일관되게 따르도록 합니다.

## 3. 퍼사드 계층(Facade) 규칙

### 규칙 3: 교차 DB 호출 시 트랜잭션 분리

- **내용:** 두 개 이상의 다른 트랜잭션 관리자를 사용하는 서비스들을 호출하는 Facade 메서드에는 **`@Transactional`을 절대 붙이지 않습니다.**
- **근거:** Facade 레벨에서 트랜잭션이 시작되면, 하위 서비스로 트랜잭션 컨텍스트가 전파되어 충돌을 일으킵니다. 트랜잭션의 책임은 각 하위 서비스에 완전히 위임해야 합니다.

- **나쁜 예시 (트랜잭션 충돌 발생):**

  ```java
  @Transactional // 금지! h2TransactionManager로 시작됨
  public void someFacadeMethod() {
      h2Service.doWork();      // h2TransactionManager 필요 (정상)
      pgService.doOtherWork(); // pgTransactionManager 필요 (충돌 발생!)
  }
  ```

- **좋은 예시 (트랜잭션 분리):**

  ```java
  // Facade 메서드에는 트랜잭션 없음
  public void someFacadeMethod() {
      // h2Service는 자체적으로 h2TransactionManager 트랜잭션을 시작하고 종료함
      h2Service.doWork();

      // pgService는 자체적으로 pgTransactionManager 트랜잭션을 시작하고 종료함
      pgService.doOtherWork();
  }
  ```

## 4. DB 설정 파일 참고 (`.../config/database`)

- `H2JpaConfig`와 `PgJpaConfig`는 각 DB의 Repository와 트랜잭션 관리자를 담당합니다.
- `h2TransactionManager`와 `h2JpaProperties`에 붙어있는 `@Primary` 어노테이션은 Spring Boot 자동 설정의 요구사항을 만족시키기 위한 최소한의 조치이며, **우리의 서비스 코드에서는 이 기본값에 의존해서는 안 됩니다.**

## 5. 외부 API 호출 시 트랜잭션 분리 (중요!)

### 규칙 4: 외부 API 호출은 트랜잭션 밖에서 실행

- **내용:** HTTP 요청, 외부 API 호출 등 네트워크 I/O가 포함된 작업은 **절대 트랜잭션 안에서 실행하지 않습니다.**
- **근거:** 외부 API 응답 대기 시간 동안 DB 커넥션을 점유하면, 커넥션 풀이 고갈되어 서버 전체가 멈출 수 있습니다.

- **나쁜 예시 (커넥션 장시간 점유):**

  ```java
  @Transactional("pgTransactionManager")
  public List<Plan> findSimilarPlans(Long planId) {
      // DB 조회 - 커넥션 획득
      PlanEmbedding embedding = repository.findById(planId)...

      // 외부 API 호출 - 응답 대기 중에도 커넥션 점유! ❌
      float[] vector = callGeminiAPI(embedding);

      // DB 조회 - 여전히 같은 커넥션 사용
      return repository.findSimilar(vector);
  }
  ```

- **좋은 예시 (트랜잭션 분리):**

  ```java
  // 트랜잭션 없이 실행
  public List<Plan> findSimilarPlans(Long planId) {
      // 1단계: 짧은 트랜잭션 - DB 조회만
      PlanEmbedding embedding = findEmbeddingById(planId);

      // 2단계: 트랜잭션 밖 - 외부 API 호출
      float[] vector = callGeminiAPI(embedding);

      // 3단계: 새로운 짧은 트랜잭션 - DB 조회만
      return findSimilarWithVector(vector);
  }

  @Transactional(value = "pgTransactionManager", readOnly = true)
  private PlanEmbedding findEmbeddingById(Long planId) { ... }

  @Transactional(value = "pgTransactionManager", readOnly = true)
  private List<Plan> findSimilarWithVector(float[] vector) { ... }
  ```

## 6. 배치 작업 최적화

### 규칙 5: 반복적인 DB 작업은 배치로 처리

- **내용:** 반복문 안에서 `save()`, `delete()` 등을 개별적으로 호출하지 말고, `saveAll()`, `deleteAll()` 등의 배치 메서드를 사용합니다.
- **근거:** 개별 호출은 매번 DB 커넥션을 사용하여 커넥션 풀을 빠르게 소진시킵니다.

- **나쁜 예시 (132번 커넥션 사용):**

  ```java
  for (int i = 0; i <= 10; i++) {
      LocationTrack track = LocationTrack.builder()...
      locationTrackRepository.save(track); // 11번 개별 호출! ❌
  }
  ```

- **좋은 예시 (1번 커넥션 사용):**

  ```java
  List<LocationTrack> tracks = new ArrayList<>();
  for (int i = 0; i <= 10; i++) {
      LocationTrack track = LocationTrack.builder()...
      tracks.add(track);
  }
  locationTrackRepository.saveAll(tracks); // 한 번에 저장! ✅
  ```

- **효과:** 3개 시나리오 × 4명 참가자 × 11개 트랙 = 132개 개별 save → 12개 saveAll로 감소 (91% 개선)

## 7. 실제 사례: DB 커넥션 폭풍 (2025-12-02)

### 발생 원인

1. **Facade 트랜잭션 규칙 위반**: `PlanFacade`가 클래스 레벨에 `@Transactional("h2TransactionManager")`를 선언하여, 교차 DB 호출 메서드에서도 트랜잭션이 전파됨
2. **외부 API 호출이 트랜잭션 내부**: `PlanEmbeddingService`가 Gemini API 호출을 PostgreSQL 트랜잭션 안에서 실행
3. **대량 개별 저장**: 132개의 LocationTrack을 반복문으로 개별 저장

### 해결 방법

1. Facade 클래스 레벨 트랜잭션 제거, 각 메서드별로 개별 명시
2. 외부 API 호출을 트랜잭션 밖으로 분리
3. 배치 저장 적용

### 교훈

- **규칙 3**을 위반하면 서버 전체가 멈출 수 있습니다.
- **규칙 4**를 위반하면 커넥션 풀이 고갈됩니다.
- 작은 최적화(배치 저장)가 큰 효과를 냅니다.
