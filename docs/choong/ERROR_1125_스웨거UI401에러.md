# [가이드] Swagger UI에서 발생하는 401 Unauthorized 에러 트러블슈팅

**작성일:** 2025-11-25
**목표:** `curl` 이나 Postman 등에서는 정상 작동하지만, 유독 Swagger UI에서만 API 호출 시 401 에러가 발생하는 문제의 원인을 진단하고 해결하는 과정을 안내합니다.

---

## 1. 문제 상황

- **증상:** 특정 컨트롤러의 API를 Swagger UI에서 호출하면, `Authorization` 헤더가 누락되어 서버로부터 401 Unauthorized 응답을 받는다.
- **서버 로그:** `AuthInterceptor`에서 `Authorization header: null` 과 `Token is null or empty` 경고가 발생하며, 경우에 따라 `JwtTokenProvider` 내부에서 `NullPointerException`이 발생할 수 있다.
- **특이 사항:** `curl` 이나 Postman과 같은 다른 도구로 동일한 토큰을 사용하여 테스트하면 API가 정상적으로 호출된다.

---

## 2. 원인 분석

이 문제의 원인은 복합적이지만, 크게 **클라이언트(Swagger UI) 설정**과 **서버의 안정성** 두 가지로 나눌 수 있습니다.

### 2.1. 직접적 원인: Swagger UI의 `Authorization` 헤더 누락

가장 직접적인 원인은 Swagger UI가 서버로 요청을 보낼 때, `Authorization` 헤더를 포함시키지 않았기 때문입니다.

### 2.2. 근본 원인 1: Swagger UI 설정 누락

`curl`에서는 되는데 Swagger UI에서만 안 되는 이유는, Swagger UI가 해당 API가 인증을 필요로 한다는 사실을 인지하지 못했기 때문입니다.

`PlanRestController`는 정상 작동했지만 `GroupController`는 그렇지 않았던 이유는, `PlanRestController` 클래스 레벨에만 다음과 같은 어노테이션이 있었기 때문입니다.

```java
@SecurityRequirement(name = "Bearer Authentication")
```

이 어노테이션은 Swagger UI에게 "이 컨트롤러의 모든 API는 `SwaggerConfig`에 정의된 'Bearer Authentication' 방식의 인증이 필요하니, 'Authorize' 버튼으로 입력된 토큰을 모든 요청에 자동으로 포함시켜라"고 알려주는 역할을 합니다. 이 설정이 `GroupController`에 누락되어 헤더 전송이 이루어지지 않았습니다.

### 2.3. 근본 원인 2: 서버 안정성 부족

클라이언트가 잘못된 요청을 보내더라도, 서버가 `NullPointerException`으로 비정상적인 오류를 내뿜는 것은 바람직하지 않습니다. `AuthInterceptor`가 `null` 토큰을 `JwtTokenProvider`로 그대로 전달하고, `JwtTokenProvider`가 `null`에 대한 방어 코드가 부족했던 것이 서버 안정성을 저해하는 요인이었습니다.

---

## 3. 해결 과정

### 3.1. 서버 안정성 강화: `JwtTokenProvider` Null 방어

클라이언트의 잘못된 요청에도 서버가 안정적으로 401 응답을 주도록 `JwtTokenProvider.java`의 `validateToken`과 `isBlacklisted` 메서드에 `null` 또는 빈 문자열(`isBlank`)을 체크하는 로직을 추가했습니다.

**`validateToken` 수정 후:**
```java
public boolean validateToken(String token) {
    // null 또는 빈 문자열(공백 포함) 토큰 체크 추가
    if (token == null || token.isBlank()) {
        log.warn("Token is null or blank. Validation failed.");
        return false;
    }
    // ... (이하 로직)
}
```

### 3.2. Swagger UI 설정 통일

문제가 발생했던 `GroupController.java` 클래스 레벨에 `@SecurityRequirement` 어노테이션을 추가하여, Swagger UI가 인증 토큰을 정상적으로 헤더에 포함하도록 수정했습니다.

**`GroupController` 수정 후:**
```java
@Slf4j
@Tag(name = "Group API", description = "그룹 및 채팅 관련 API")
@RestController
@RequiredArgsConstructor
@RequestMapping("/api/groups")
@SecurityRequirement(name = "Bearer Authentication") // <<< 이 부분 추가
public class GroupController {
    // ...
}
```

### 3.3. (부가) 컨트롤러 코드 스타일 통일

코드의 일관성을 높이고 향후 유지보수를 용이하게 하기 위해, `@RequestAttribute`를 사용하던 `GroupController`의 모든 메서드를 `HttpServletRequest`를 직접 받아 처리하는 방식으로 통일했습니다.

---

## 4. 핵심 요약 및 교훈

1.  **`curl` vs UI 도구:** `curl`과 같은 로우 레벨(low-level) 도구에서 API가 정상 작동한다면, 서버의 핵심 로직보다는 클라이언트나 중간 설정(Swagger UI, 프록시 등)의 문제일 가능성이 높다.
2.  **Swagger 어노테이션의 중요성:** `@SecurityRequirement`와 같은 Swagger 관련 어노테이션은 애플리케이션의 동작에 직접적인 영향을 주지는 않지만, **API 문서화 및 테스트 편의성에 결정적인 역할**을 한다. 인증이 필요한 컨트롤러에는 반드시 추가하여 일관성을 유지하자.
3.  **방어적 프로그래밍:** 클라이언트가 언제나 올바른 요청을 보낼 것이라고 가정해서는 안 된다. `null` 이나 비정상적인 값이 들어올 가능성이 있는 부분(특히 외부 입력을 받는 경계)에는 항상 방어 코드를 추가하여 서버의 안정성을 높여야 한다.
