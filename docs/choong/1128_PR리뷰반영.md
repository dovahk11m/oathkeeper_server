## 1. PR 리뷰 반영 사항

### 1.1. MetricsPushService.java - JPA 변경 감지 활용

**리뷰 내용:**

> `@Transactional` 어노테이션을 추가하여 복구 로직의 원자성을 보장한 점은 좋은 개선입니다.
> 이 어노테이션으로 인해, 메서드 내에서 조회된 엔티티는 영속성 컨텍스트에서 관리되며, 변경 사항은 트랜잭션 커밋 시점에 자동으로 데이터베이스에 반영됩니다(이를 'dirty checking' 또는 변경 감지라고 합니다).
> 따라서 `recoverFetchAndSavePlanSummary` 메서드 내부의 `planJpaRepository.save(plan)` 호출은 더 이상 필요하지 않습니다.

**파일:** `src/main/java/com/oath/domain/metrics/service/MetricsPushService.java`

**변경 내용:**

```diff
@Recover
@Transactional("h2TransactionManager")
public void recoverFetchAndSavePlanSummary(Exception e, Long planId) {
    log.error("[plan-summary-fetch][RECOVER] planId={}의 요약 보고서 수신에 최종 실패했습니다. 원인: {}", planId,
            e.getMessage());
    planJpaRepository.findById(planId).ifPresent(plan -> {
        plan.setSummary("AI 요약 생성에 실패했습니다: " + e.getMessage());
        plan.setSummaryStatus(SummaryStatus.FAILED);
-       planJpaRepository.save(plan);
+       // JPA 변경 감지(dirty checking)로 자동 저장되므로 save() 호출 불필요
    });
}
```

**개선 효과:**

- ✅ JPA의 변경 감지 메커니즘을 올바르게 활용
- ✅ 불필요한 메서드 호출 제거로 코드 간결성 향상
- ✅ 같은 클래스 내 `fetchAndSavePlanSummary` 메서드와 일관성 확보

**핵심 원리:**

- `@Transactional` 어노테이션이 있으면 영속성 컨텍스트가 활성화됨
- `findById()`로 조회된 엔티티는 영속 상태로 관리됨
- 엔티티 변경 시 트랜잭션 커밋 시점에 자동으로 UPDATE 쿼리 실행
- 따라서 명시적인 `save()` 호출이 불필요함

## 4. 앞으로 주의해야 할 사항 (반성)

### 4.1. JPA 영속성 컨텍스트 이해 부족

**문제:**

- `@Transactional` 어노테이션이 있는 메서드에서 불필요한 `save()` 호출
- JPA의 변경 감지(dirty checking) 메커니즘을 제대로 활용하지 못함

**반성:**

- JPA의 핵심 원리를 충분히 이해하지 못한 채 코드 작성
- "일단 save()를 호출하면 안전하겠지"라는 안일한 생각

**개선 방안:**

1. **영속성 컨텍스트 라이프사이클 학습**

   - `@Transactional` 범위 내에서 엔티티 상태 변화 이해
   - 영속, 준영속, 비영속 상태 구분
   - 변경 감지 시점과 플러시 타이밍 이해

2. **코드 작성 전 원리 확인**

   - "왜 save()를 호출해야 하는가?" 질문하기
   - 같은 클래스 내 다른 메서드와 일관성 확인
   - 불필요한 코드는 과감히 제거

3. **참고 문서 작성**
   - JPA 변경 감지 원리를 ERROR 문서로 정리
   - 향후 유사한 실수 방지

### 4.2. Null 안전성에 대한 경각심 부족

**문제:**

- `authHeader.startsWith()` 호출 전 명시적 null 체크 누락
- `StringUtils.hasText()`에 의존하여 IDE 경고 무시

**반성:**

- "StringUtils가 알아서 처리하겠지"라는 막연한 믿음
- IDE 경고를 "나중에 처리하면 되지"라고 미루는 습관
- Null 안전성을 "컴파일되면 괜찮다"는 수준으로만 생각

**개선 방안:**

1. **명시적 null 체크 습관화**

   - 외부 입력값은 항상 null 가능성 고려
   - IDE 경고를 즉시 확인하고 판단
   - `@NonNull`, `@Nullable` 어노테이션 적극 활용

2. **방어적 프로그래밍**

   - "이 변수가 null일 수 있는가?" 항상 질문
   - 특히 WebSocket, HTTP 헤더 등 외부 입력은 더욱 주의
   - Early return 패턴 활용

3. **IDE 경고 즉시 대응**
   - 경고 발생 시 "왜 발생했는가?" 분석
   - False Positive 판단은 신중하게
   - 실제 문제는 즉시 수정

### 4.3. 코드 리뷰의 중요성 재인식

**반성:**

- 혼자 작성한 코드는 "당연히 맞다"고 생각하는 경향
- 리뷰어의 피드백이 없었다면 발견하지 못했을 문제들

**개선 방안:**

1. **자기 코드 리뷰 습관**

   - 커밋 전 본인이 먼저 리뷰
   - "이 코드를 처음 보는 사람이 이해할 수 있는가?" 질문
   - 불필요한 코드, 중복 코드 제거

2. **리뷰 피드백 적극 수용**

   - 리뷰 의견은 학습 기회로 활용
   - "왜 이렇게 해야 하는가?" 원리 이해
   - 유사한 패턴이 있는지 전체 코드베이스 검토

3. **지식 문서화**
   - 리뷰에서 배운 내용을 문서로 정리
   - ERROR 문서, 코딩 가이드 업데이트
   - 팀원과 지식 공유
