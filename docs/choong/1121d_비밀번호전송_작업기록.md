# 1121d: 임시 비밀번호 발급 및 메일 전송 기능 리팩토링

## 1. 개요

- **목표:** 사용자가 비밀번호를 잊었을 때, 이메일로 임시 비밀번호를 발급하는 기능을 구현하고, 도메인 간 결합도를 낮추기 위해 스프링 이벤트를 활용하여 리팩토링을 진행함.
- **초기 문제:** `MemberService` 내에서 임시 비밀번호를 생성하고, `JavaMailSender`를 직접 주입받아 메일 발송 로직까지 처리하려고 시도했으나, 이는 `MemberService`가 알림(메일) 도메인의 책임까지 갖게 되어 SRP(단일 책임 원칙)에 위배되고 도메인 간 결합도를 높이는 문제점이 있었음.

## 2. 1차 구현 (리팩토링 전)

- **파일:** `src/main/java/com/oath/domain/members/service/MemberService.java`
- **구현 내용:**
    1. `sendTemporaryPassword` 메서드 내에서 임의의 8자리 임시 비밀번호를 생성.
    2. 해당 회원의 비밀번호를 임시 비밀번호로 업데이트.
    3. `JavaMailSender`를 사용하여 회원 이메일로 임시 비밀번호를 직접 발송.
- **문제점:**
    - `MemberService`가 `JavaMailSender`에 직접 의존하게 되어, 향후 알림 방식이 SMS, 카카오톡 등으로 확장될 경우 `MemberService`의 코드를 계속 수정해야 함.
    - 회원 도메인의 핵심 로직과 알림 발송이라는 부가 기능이 강하게 결합되어 유지보수가 어려움.

## 3. 2차 구현 (스프링 이벤트 기반 리팩토링)

- **목표:** `MemberService`와 알림 서비스의 결합도를 낮추고, 확장성 있는 구조로 개선.
- **리팩토링 전략:** 스프링의 `ApplicationEventPublisher`를 사용하여 "비밀번호 재설정" 이라는 도메인 이벤트를 발행하고, 별도의 리스너가 이 이벤트를 받아 메일 발송을 처리하도록 역할을 분리함.

### 3.1. `PasswordResetEvent` 정의

- **신규 파일:** `src/main/java/com/oath/domain/members/memberEvent/PasswordResetEvent.java`
- **구현 내용:**
    - 이벤트에 필요한 데이터(수신자 이메일, 사용자 이름, 임시 비밀번호)를 담는 `PasswordResetEvent` 클래스를 생성.

### 3.2. `PasswordResetListener` 정의

- **신규 파일:** `src/main/java/com/oath/domain/members/memberEvent/PasswordResetListener.java`
- **구현 내용:**
    - `@TransactionalEventListener`를 사용하여 `PasswordResetEvent`를 구독하는 리스너를 구현.
    - `AlarmFactory`를 주입받아, 이벤트에 담긴 정보를 바탕으로 실제 메일 발송을 위임.
    - `@Async`를 적용하여 메일 발송이 비동기적으로 처리되도록 하여, 사용자 응답 시간을 단축.

### 3.3. `MemberService` 수정

- **수정 파일:** `src/main/java/com/oath/domain/members/service/MemberService.java`
- **구현 내용:**
    - `JavaMailSender`에 대한 직접적인 의존성을 제거.
    - `ApplicationEventPublisher`를 주입받음.
    - `sendTemporaryPassword` 메서드에서 임시 비밀번호 생성 및 회원 정보 업데이트 후, `PasswordResetEvent`를 발행(`eventPublisher.publishEvent(...)`)하는 로직으로 변경.

## 4. 결과

- `MemberService`는 이제 알림 발송 방식(이메일, SMS 등)을 전혀 알지 못하며, 오직 "비밀번호가 재설정되었다"는 사실만 이벤트로 발행하는 책임만 가짐.
- `PasswordResetListener`가 메일 발송의 책임을 담당하게 되어, 향후 다른 알림 방식을 추가하더라도 `MemberService`의 수정 없이 새로운 리스너를 추가하는 것만으로 유연하게 확장 가능.
- 도메인 간 결합도가 낮아지고, 각 서비스의 책임이 명확해져 코드의 유지보수성과 테스트 용이성이 크게 향상됨.
