# 1021: 프로젝트 재구성 제안서

- **목적:** 사용자 경험의 흐름을 더 명확히 하고, 앱의 핵심 가치인 '공정성'과 '신뢰'가 어떻게 전달되는지 구체적으로 보여주기 위해 시나리오와 DB 설계를 재구성.

---

## 1. 사용자 시나리오 (재구성)

### 등장인물

-   **지훈 (기획자):** 경기도 남부(동탄) 거주. 모임을 주도하며 공정한 약속을 중시함.
-   **민수 (개발자):** 경기도 동부(남양주) 거주. 약속에 늦지는 않지만, 이동 거리에 민감함.
-   **수빈 (디자이너):** 경기도 북부(의정부) 거주. 약속 준비에 시간이 걸려 가끔 아슬아슬하게 도착함.
-   **그룹:** '바보들'

---

### 시나리오 1: 첫 번째 약속 - 신뢰의 데이터화

1.  **약속 생성 및 그룹 결성:**
    -   지훈이 앱에서 `+ 새 약속` 버튼을 누릅니다.
    -   약속방 이름을 '바보들 10월 정모'로 설정하고, 카카오톡으로 민수와 수빈을 초대합니다.
    -   초대된 멤버들이 수락하면, '바보들'이라는 그룹이 자동으로 생성되어 다음 약속에 재사용할 수 있습니다.
2.  **'공정성 엔진'의 첫 가동:**
    -   지훈이 약속의 목적 키워드로 `#식사`, `#술`, `#인스타`를 선택합니다.
    -   앱이 세 사람의 현재 위치(또는 저장된 기본 위치)를 기반으로 '이동 시간 편차가 가장 적은' 최적 장소 후보들을 계산합니다.
    -   **UI 제시:** "모두의 이동 시간을 고려했을 때, 건대입구가 가장 공평해요! (예상 시간: 지훈 85분, 민수 70분, 수빈 80분)" 와 같이 추천의 근거를 명확히 보여줍니다.
3.  **출발 및 실시간 검증:**
    -   약속 시간이 다가오자, 각 멤버에게 개인화된 출발 시간 알림이 도착합니다. (예: "지훈님, 85분 소요 예정! 늦어도 1시 45분에는 출발해야 해요!")
    -   수빈이 '출발' 버튼을 누르지만, 5분간 GPS 좌표에 변화가 없자 시스템이 부드러운 알림을 보냅니다. "수빈님, 아직 출발 준비 중이신가요? 😮"
    -   지도 위에는 각 멤버의 아이콘이 실시간으로 움직이며, "민수님, 강변북로 진입! 25분 후 도착 예정"과 같은 상태 메시지가 표시됩니다.
4.  **결과 및 피드백 루프:**
    -   약속 장소 반경 100m 내에 진입 시, 도착이 자동으로 기록됩니다.
    -   약속 종료 후, 결과 화면에 타임라인이 표시됩니다.
        -   14:50 지훈님 도착 (+10분)
        -   15:00 민수님 도착 (정시)
        -   15:15 수빈님 도착 (-15분)
    -   Oathkeeper 등급 경험치가 상승하고, 지훈은 '성실 포인트'를 획득합니다. 이 포인트는 다음 약속의 '공정성' 계산에 가중치로 사용됩니다.

---

### 시나리오 2: 두 번째 약속 - 누적된 신뢰의 보상

1.  **익명으로 시작하는 제안:**
    -   며칠 후, 지훈이 앱의 '바보들' 그룹 페이지에서 `다음 약속 제안하기` 버튼을 누릅니다.
    -   "10월 말 주말 어때?"라는 메시지와 함께 가능한 날짜 여러 개를 선택하여 투표를 부칩니다. 제안은 지훈의 이름이 아닌 '그룹 관리자'의 이름으로 발송되어 부담을 줄여줍니다.
2.  **데이터 기반의 장소 추천:**
    -   멤버들의 투표로 11월 3일이 약속일로 확정됩니다.
    -   장소 추천 단계에서 앱이 새로운 제안을 합니다.
    -   **UI 제시:** "지난 약속에서 지훈님이 가장 오래 이동했어요. 누적된 성실 포인트를 반영해서, 이번엔 역삼역 근처는 어떠세요? (예상 시간: 지훈 50분, 민수 90분, 수빈 95분)"
    -   멤버들은 이 제안을 수락하거나, 다른 장소를 선택할 수 있는 자율권을 가집니다.
3.  **선순환의 완성:**
    -   멤버들이 '역삼역' 제안을 수락합니다. 지훈은 이동 부담을 덜고, 민수와 수빈은 지난 약속의 '사회적 부채'를 해소하며 그룹의 공정성을 유지합니다.
    -   약속이 성공적으로 끝나고, 모든 멤버의 Oathkeeper 등급이 상승하며 긍정적인 경험이 강화됩니다. 이는 다음 약속을 다시 '약속 지킴이' 앱으로 잡게 만드는 강력한 동기가 됩니다.

## 2. 데이터베이스 설계 (재설계)

-   **주요 변경 원칙:**
    1.  **확장성 확보:** 수십억 건으로 늘어날 수 있는 위치 스냅샷 저장을 회피하고, 출발/도착 등 핵심 이벤트만 기록하여 DB 부하를 원천적으로 방지합니다.
    2.  **개념 모델링 강화:** 기획안의 핵심인 '그룹'과 '다음 약속 제안' 기능을 명시적인 테이블로 설계하여 기능을 안정적으로 지원합니다.
    3.  **성능 최적화:** 위도/경도를 단순 숫자 대신 공간 데이터를 위한 `POINT` 타입으로 저장하여, 향후 위치 기반 쿼리(예: "주변 장소 찾기") 성능을 보장합니다.

### 신규 테이블 스키마

| 테이블 | 컬럼명 | 설명 |
| --- | --- | --- |
| `groups` (신규) | `id` (PK) | 그룹 식별자 |
| | `group_name` | 그룹 이름 (예: '바보들') |
| | `created_at` | 생성 일시 |
| `group_members` (신규) | `id` (PK) | 관계 식별자 |
| | `group_id` (FK) | groups.id |
| | `member_id` (FK) | members.id |
| | `role` | 그룹 내 역할 (예: ADMIN, MEMBER) |
| `plans` (구 `promises`) | `id` (PK) | 약속 식별자 |
| | `group_id` (FK) | 약속이 속한 그룹 ID (groups.id) |
| | `title` | 약속 제목 |
| | `plan_datetime` | 약속 일시 |
| | `status` | 약속 상태 (예: PROPOSED, CONFIRMED) |
| | `place_name` | 확정된 장소명 |
| | `place_location` | 확정된 장소 좌표 (POINT 타입) |
| `plan_participants` | `id` (PK) | 약속 참가자 식별자 |
| | `plan_id` (FK) | plans.id |
| | `member_id` (FK) | members.id |
| | `start_location` | 출발지 좌표 (POINT 타입) |
| | `arrival_status` | 도착 상태 (예: ON_TIME, LATE) |
| | `arrival_offset_minutes` | 약속 시간 대비 도착 시간 차이 (분) |
| `location_events` (구 `location_snapshots` 대체) | `id` (PK) | 위치 이벤트 식별자 |
| | `participant_id` (FK) | plan_participants.id |
| | `event_type` | 이벤트 타입 (예: DEPARTURE, ARRIVAL) |
| | `location` | 이벤트 발생 좌표 (POINT 타입) |
| | `timestamp` | 이벤트 발생 시각 |
| `plan_proposals` (신규) | `id` (PK) | 약속 제안 식별자 |
| | `group_id` (FK) | 제안이 발생한 그룹 ID (groups.id) |
| | `proposer_member_id` (FK) | 제안자 ID (익명 제안 시 NULL) |
| | `message` | 제안 메시지 (예: "10월 말 2차 모임 어때요?") |
| `proposal_votes` (신규) | `id` (PK) | 투표 식별자 |
| | `proposal_id` (FK) | plan_proposals.id |
| | `member_id` (FK) | 투표한 멤버 ID (members.id) |
| | `selected_datetime` | 멤버가 선택한 날짜/시간 |

*기존 `members`, `places`, `reviews`, `chat`, `fines` 등 다른 테이블들은 현재 설계가 좋으므로 유지합니다.*

## 3. 역할 분담 (재구성)

- **방법론:** 애자일(Agile) 방법론의 스프린트(Sprint) 개념을 도입하여, 기능 단위로 역할을 재구성하는 것을 제안.

### 스프린트 1: MVP 핵심 기능 구현 (1~4주차)

-   **목표:** 사용자가 약속을 생성하고, 공정한 장소를 추천받아, 도착 여부를 기록하는 핵심 사이클을 완성한다.

| 기능 Epic (단위) | 담당자 | 주요 과업 및 학습 목표 |
| --- | --- | --- |
| 1. 약속 도메인 설계 및 구현 | 문한영 | `plans`, `participants` 등 핵심 도메인 API 전체를 책임지고 구현. (도메인 완전 정복 목표 달성) |
| 2. 공정성 추천 엔진 (백엔드) | 김성훈 | 여러 참여자의 위치를 받아 '이동 시간 편차 최소화' 알고리즘을 구현하고 API 제공. (데이터/AI 관심사 부합) |
| 3. 지도 및 위치 시각화 (프론트엔드) | 양성빈 | Flutter에서 지도(Kakao/Naver)를 띄우고, 추천 장소와 사용자 위치를 표시. (지도/AI 관심사 부합) |
| 4. 사용자 인증 및 그룹 관리 | 김세리 | 소셜 로그인 구현 및 신규 `groups`, `group_members` 테이블 관련 API 개발. (단순 CRUD 이상 경험) |
| 5. 프로젝트 총괄 및 인프라 | 조충희 | 프로젝트 초기 설정, Git 전략 수립, CI/CD 구축 및 팀 전체의 기술적 문제 해결 지원. (리더십) |

### 스프린트 2: 신뢰도 및 편의 기능 구현 (5~8주차)

-   **목표:** 실시간 추적의 신뢰도를 높이고, 반복 사용을 유도하는 편의 기능을 추가한다.

| 기능 Epic (단위) | 담당자 | 주요 과업 및 학습 목표 |
| --- | --- | --- |
| 1. 실시간 위치 추적 및 검증 | 김성훈 (백엔드), 양성빈 (프론트엔드) | (페어 프로그래밍) Flutter에서 위치 정보를 받아 Redis에 캐시하고, Spring에서 GPS 미변화 등을 감지하는 로직 구현. |
| 2. 2차 약속 제안 및 투표 시스템 | 김세리 | `plan_proposals`, `proposal_votes`를 이용한 익명 제안 및 자동 조율 기능 전체 구현. (복잡한 상태 관리 경험) |
| 3. 알림 시스템 및 로그 | 문한영 | FCM을 이용한 출발 독촉, 지각 등 상황별 알림 시스템 구축. |
| 4. 장소 리뷰 및 사진 공유 | 조충희 | 약속 종료 후 장소에 대한 후기를 작성하고 공유하는 기능 구현. |
