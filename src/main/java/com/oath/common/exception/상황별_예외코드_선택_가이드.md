# 상황별 예외 코드 선택 가이드

이 문서는 `com.oath.common.exception` 패키지에 정의된 커스텀 예외 클래스들을 언제, 어떻게 사용해야 하는지에 대한 가이드라인을 제공합니다. 올바른 예외 코드 사용은 클라이언트에게 명확한 피드백을 제공하고, API의 일관성을 유지하며, 디버깅 효율성을 높이는 데 중요합니다.

`MyExceptionHandler`에서 이 예외들을 전역적으로 처리하여 `CommonResponse` 형식으로 클라이언트에 응답합니다.

---

## 1. `Exception400` (Bad Request)

-   **설명**: 클라이언트의 요청이 유효하지 않거나, 서버가 처리할 수 없는 형식일 때 사용합니다. 주로 비즈니스 로직 상의 유효성 검사 실패나 잘못된 데이터 형식에 해당합니다.
-   **HTTP 상태 코드**: `400 Bad Request`
-   **주요 사용 상황**:
    *   요청 파라미터나 요청 본문의 데이터가 유효성 검사를 통과하지 못했을 때 (예: 필수 필드 누락, 형식 오류, 값 범위 초과).
    *   비즈니스 규칙 위반 (예: 이미 존재하는 리소스 생성 시도, 특정 상태에서 허용되지 않는 작업).
    *   비밀번호 불일치 (로그인 시도 시).
    *   인증 토큰 만료 (이메일 인증 등).
    *   유효하지 않은 토큰 (JWT 토큰 등).
-   **예시**:
    ```java
    throw new Exception400("비밀번호가 일치하지 않습니다.");
    throw new Exception400("인증 토큰이 만료되었습니다. 다시 가입해주세요.");
    throw new Exception400("유효하지 않은 요청 데이터입니다.");
    ```

---

## 2. `Exception401` (Unauthorized)

-   **설명**: 클라이언트가 인증되지 않았거나, 유효한 인증 자격 증명(예: 토큰)을 제공하지 않았을 때 사용합니다. 로그인 실패와 같이 **인증 과정에서 문제가 발생**했을 때 주로 사용됩니다.
-   **HTTP 상태 코드**: `401 Unauthorized`
-   **주요 사용 상황**:
    *   로그인 시도 시 이메일 또는 비밀번호가 일치하지 않을 때 (사용자 열거 취약점 방지를 위해 일반적인 메시지 사용).
    *   이메일 인증이 완료되지 않은 계정으로 로그인을 시도할 때.
    *   비활성화되거나 휴면 상태인 계정으로 로그인을 시도할 때.
    *   유효하지 않거나 만료된 인증 토큰으로 보호된 리소스에 접근하려 할 때 (JWT 검증 실패 등).
-   **예시**:
    ```java
    throw new Exception401("이메일 또는 비밀번호가 일치하지 않습니다.");
    throw new Exception401("이메일 인증이 완료되지 않은 계정입니다. 이메일을 확인해주세요.");
    throw new Exception401("유효하지 않은 인증 정보입니다.");
    ```

---

## 3. `Exception403` (Forbidden)

-   **설명**: 클라이언트가 인증되었지만, 요청된 리소스에 접근할 **권한이 없을 때** 사용합니다. 인증은 성공했으나, 해당 작업에 대한 인가(Authorization)가 실패한 경우입니다.
-   **HTTP 상태 코드**: `403 Forbidden`
-   **주요 사용 상황**:
    *   일반 사용자(USER)가 관리자(ADMIN)만 접근 가능한 리소스에 접근하려 할 때.
    *   다른 사용자의 정보를 수정하거나 삭제하려 할 때.
    *   특정 역할(Role)이 필요한 기능에 해당 역할이 없는 사용자가 접근하려 할 때.
-   **예시**:
    ```java
    throw new Exception403("해당 작업에 대한 권한이 없습니다.");
    throw new Exception403("관리자만 접근할 수 있는 리소스입니다.");
    ```

---

## 4. `Exception404` (Not Found)

-   **설명**: 요청된 리소스를 서버에서 찾을 수 없을 때 사용합니다. 클라이언트가 존재하지 않는 URL에 접근했거나, 유효하지 않은 ID로 리소스를 조회/조작하려 할 때 발생합니다.
-   **HTTP 상태 코드**: `404 Not Found`
-   **주요 사용 상황**:
    *   특정 ID를 가진 사용자, 게시물, 약관 등을 찾을 수 없을 때.
    *   존재하지 않는 경로(URL)로 요청이 들어왔을 때 (Spring 기본 핸들러가 처리하는 경우가 많음).
    *   유효하지 않은 인증 토큰 (이메일 인증 시 토큰이 DB에 없을 때).
-   **예시**:
    ```java
    throw new Exception404("일치하는 회원을 찾을 수 없습니다.");
    throw new Exception404("요청하신 게시물을 찾을 수 없습니다.");
    throw new Exception404("유효하지 않은 인증 토큰입니다.");
    ```

---

## 5. `Exception409` (Conflict)

-   **설명**: 클라이언트의 요청이 서버의 현재 리소스 상태와 충돌할 때 사용합니다. 주로 데이터의 중복이나 동시성 문제와 관련이 있습니다.
-   **HTTP 상태 코드**: `409 Conflict`
-   **주요 사용 상황**:
    *   이미 존재하는 이메일로 회원가입을 시도할 때.
    *   고유해야 하는 필드(예: 사용자 ID, 닉네임)가 중복될 때.
    *   동시성 제어(Optimistic Locking)에서 충돌이 발생했을 때.
-   **예시**:
    ```java
    throw new Exception409("이미 사용 중인 이메일입니다.");
    throw new Exception409("이미 존재하는 닉네임입니다.");
    ```

---

## 6. `Exception500` (Internal Server Error)

-   **설명**: 서버가 요청을 처리하는 과정에서 예상치 못한 오류가 발생했을 때 사용합니다. 이는 클라이언트의 잘못이 아닌, 서버 내부의 문제임을 나타냅니다.
-   **HTTP 상태 코드**: `500 Internal Server Error`
-   **주요 사용 상황**:
    *   데이터베이스 연결 오류, 외부 시스템 연동 오류 등 서버 내부에서 복구 불가능한 예외가 발생했을 때.
    *   개발자가 예상하지 못한 `RuntimeException`이 발생하여 `MyExceptionHandler`의 일반 `RuntimeException` 핸들러에 의해 처리될 때.
-   **예시**:
    ```java
    // 일반적으로 비즈니스 로직에서 직접 던지기보다는, 예상치 못한 런타임 예외가 발생했을 때
    // MyExceptionHandler의 RuntimeException 핸들러에 의해 처리되도록 합니다.
    // 특정 상황에서 명시적으로 던져야 한다면:
    throw new Exception500("데이터 처리 중 알 수 없는 오류가 발생했습니다. 관리자에게 문의해주세요.");
    ```

---

## 7. `RuntimeException` (Fallback)

-   **설명**: 위에서 정의된 특정 HTTP 상태 코드 예외에 해당하지 않는, 모든 예상치 못한 런타임 예외를 처리하는 최후의 보루입니다. `MyExceptionHandler`의 `handleRuntimeException` 메서드에 의해 처리됩니다.
-   **HTTP 상태 코드**: `500 Internal Server Error`
-   **주요 사용 상황**:
    *   개발자가 미처 예상하지 못했거나, 복구 불가능하다고 판단되는 모든 종류의 `RuntimeException`.
-   **주의사항**:
    *   가능한 한 구체적인 예외를 던져서 클라이언트에게 명확한 정보를 제공하는 것이 좋습니다.
    *   `RuntimeException` 핸들러는 일반적인 오류 메시지(예: "시스템 오류가 발생했습니다. 관리자에게 문의해주세요.")를 반환하여 내부 구현 정보를 노출하지 않도록 합니다.

---

## 결론

예외를 던질 때는 해당 상황에 가장 적합한 HTTP 상태 코드와 메시지를 선택하여 클라이언트와 서버 간의 명확한 통신을 유지하는 것이 중요합니다. 이 가이드를 참고하여 일관성 있는 예외 처리를 적용해 주시기 바랍니다.
